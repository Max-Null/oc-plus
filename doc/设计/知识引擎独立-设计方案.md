# 知识引擎独立 — 设计方案

> 版本：v1.1 | 日期：2026-07-30 | 状态：已审查修正

## 一、背景与动机

### 1.1 现状

`分形/search.ts` 包含 BM25 搜索引擎，但知识目录管理（扫描 `.md` 文件、解析 YAML front matter 元数据、构建索引、注入 prompt）全耦合在 `分形/fractal.ts`（2895 行）中。

```
当前架构：
┌─────────────────────────────────────────────────┐
│ fractal.ts (2895行)                              │
│ ├─ parseMeta()         — HTML 注释解析           │
│ ├─ readBlocksDir()     — 目录扫描（flat+子目录） │
│ ├─ mergeBlocksAndTriggers() — 元数据合并         │
│ ├─ extractBlockValue() — 正文提取                │
│ ├─ getBlocksCached()   — 5s 缓存                 │
│ ├─ S3 注入逻辑         — BM25 rebuild + search   │
│ └─ v4searchIndex       — BM25Index 全局单例      │
└─────────────────────────────────────────────────┘
         ↓ import
┌─────────────────────────┐
│ search.ts (234行)        │
│ ├─ BM25Index             │
│ ├─ tokenize()            │
│ └─ splitMixed()          │
└─────────────────────────┘
```

### 1.2 动机

1. **oc-plus 内耦合太紧**：知识引擎与分形插件混在一起，无法被其他工具复用
2. **单文件膨胀**：fractal.ts 已达 2895 行，知识管理部分约 200 行可抽出
3. **独立测试**：当前 BM25 测试覆盖了搜索引擎，但目录扫描、元数据解析、增量更新等引擎级行为无覆盖

### 1.3 目标

抽出一个**零依赖、独立可运行**的知识引擎模块，oc-plus 作为第一个消费者。

### 2.3 API 设计

```typescript
// === 类型 ===

interface BlockMeta {
  fileName: string;      // "java-sql-n-plus-1.md"
  relPath: string;       // "auto/java-sql-n-plus-1.md" or "java-sql-n-plus-1.md"
  status: string;        // "auto" | "suggest" | "pending"
  type: string;          // "knowledge" | "habit" | …
  label: string;         // 知识标题
  description: string;   // 一句话摘要
  priority: number;      // 权重 0-100
  body: string;          // 正文首 200 字
}

interface SearchResult {
  doc: BlockMeta;
  score: number;
}

interface EngineStats {
  totalBlocks: number;   // 目录中的 .md 文件总数
  indexed: number;       // 已索引到 BM25 的文档数
}

// === 主类 ===

class KnowledgeEngine {
  /**
   * @param dirs  知识目录路径列表（支持多目录合并）
   * @param opts  可选：bodyLength（正文截断长度，默认 200）
   */
  constructor(dirs: string[], opts?: { bodyLength?: number });

  /** 扫描所有目录，解析元数据，构建 BM25 索引 */
  init(): void;

  /** BM25 搜索（同步，纯内存操作） */
  search(query: string, topK?: number): SearchResult[];

  /** 返回所有已索引的 knowledge block 元数据 */
  list(): BlockMeta[];

  /** 返回索引统计 */
  stats(): EngineStats;

  /** 手动重建索引（批量重新扫描） */
  refresh(): void;
}
```

### 2.4 关键设计决策

| # | 决策 | 选项 | 选型理由 |
|---|------|------|----------|
| 1 | **搜索同步 vs 异步** | 同步 | BM25 100 篇文档延迟 < 0.1ms，无 IO 需求 |
| 2 | **init() 同步 vs 异步** | 同步 | 依赖 `fs.readdirSync`，无网络调用 |
| 3 | **多目录合并策略** | 高优先级覆盖 | 全局 > 项目级，同名 label 后者覆盖（同 fractal 现有逻辑） |
| 4 | **是否要 fs.watch 热更新** | 不纳入 V1 | 保持简单；当前 refresh() 由 fractal 调用方按需触发 |
| 5 | **零依赖约束** | 保持 | 不引入 better-sqlite3 / js-yaml 等原生/三方依赖 |
| 6 | **Body 存储长度** | 200 字 | 首 200 字覆盖所有当前 block（最长 body ~180 字） |
| 7 | **保留 search.ts 向后兼容** | 保留但弃用 | 旧 import 路径不立即断开，加 `@deprecated` 标记 |
| 8 | **triggers 归属** | 留在 fractal | engine 只管 knowledge blocks；triggers（文件编辑审查规则）是分形专属逻辑，与知识搜索无关。fractal 已有 `readTriggersDir()` 函数，无需迁移 |

### 3.3 回源策略（何时刷新索引）

引擎启动后缓存文件系统快照。文件被外部修改时引擎不会自动感知（V1 无 fs.watch）。

| 触发源 | 频率 | 方式 | 说明 |
|--------|------|------|------|
| **fractal 的 S3 nudge 轮** | 每 5 轮 | `engine.refresh()` | nudge 轮前重建索引，保证搜索结果反映最新文件内容 |
| **新增/修改 block** | 文件写入后 | `engine.refresh()` | fractal 的 `writeKnowledgeBlock()` 写入后立即调用（同步，< 5ms） |
| **Engine 自身** | 永不 | — | engine 不主动检测文件变更，完全由调用方触发 |

> **设计原则**：引擎是纯逻辑层，不包含定时器/监听器。刷新控制权完全交给 fractal（oc-plus 唯一的消费方）。这让引擎无副作用、易于测试。

### 3.4 deploy.mjs 部署策略

为避免同时部署 `知识引擎/bm25.js` 和 `分形/search.js`（两份内容完全相同），采用重导出模式：

```
分形/search.ts → 废弃原代码，改为 re-export：
export { BM25Index, tokenize, splitMixed } from "../知识引擎/bm25.js";
```

这样：
- fractal.ts 的 `import { BM25Index } from "./search.js"` **无需修改**（零 breakage）
- deploy.mjs 只需部署 `知识引擎/bm25.js`（新文件），`分形/search.js` 部署时自动变为 re-export 内容
- 未来某版本可直接删除 `分形/search.ts`，fractal.ts 改为直接 import `../知识引擎/bm25.js`

### 3.5 暴露给 fractal 的新 functions

由于 `parseMeta`/`readBlocksDir`/`extractBlockValue` 被从 fractal 移除，引擎需暴露以下静态工具方法供 fractal 在非 knowledge 场景（如 triggers 解析）复用：

```typescript
class KnowledgeEngine {
  // … 实例方法 …

  // 静态工具：HTML 注释元数据解析（供 fractal triggers 解析复用）
  static parseMeta(content: string, maxIndex?: number): Record<string, string> | null;

  // 静态工具：目录扫描（供 fractal 扫描 triggers 目录复用）
  static scanDir(dir: string): Array<BlockMeta>;
}
```

> 注：这些静态方法是引擎主动暴露的，fractal 不需要保留本地副本。引擎的内部实现（如 `parseMeta`）天然就是静态无状态的，暴露为 static 不影响引擎架构。

## 五、风险与边界

| 风险 | 缓解 |
|------|------|
| `init()` 同步阻塞 | 当前 blocks 目录 < 50 个文件，扫描 < 5ms；未来文件量增至 500+ 时再考虑异步 |
| `parseMeta()` 行为变更 | 原样迁移，不修改解析逻辑 |
| `mergeBlocksAndTriggers` 缺失 | fractal 用 `engine.list()` 替代后，triggers 逻辑保持独立不迁移 |
| 部署后旧 search.ts 残留 | `@deprecated` 注释 + 下个版本删除 |
| OC 插件热重载 | engine 是模块级单例，通过 Node.js `require.cache` 存活。OC 热重载插件时不会重启 Node 进程 → engine 实例不丢失。但 `init()` 的目录路径依赖 `MEMORIES_DIR`（fractal 传入），若路径变量在热重载中变化，需调用 `engine.refresh()` |
